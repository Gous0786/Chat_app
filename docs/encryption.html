🛡 Aura · security notes

How your messages become unreadable to everyone but you.

Aura encrypts direct messages with the Signal Protocol — the same design behind Signal and WhatsApp. Keys are generated and kept in your browser; the server only ever handles ciphertext it cannot decrypt. Here's exactly how it works in this app.

THE IDEA IN ONE PICTURE

The same message, two points of view

When you send "let's meet at 5", two very different things are true at the same time: you and your recipient read plain words, while the database — everything the server can possibly see — holds only noise.

🔓 What you & your recipient see
let's meet at 5

Decrypted in the browser with a key only the two of you hold.

🔒 What the server stores
{"v":1,"type":3,"body":"MyjpAgiRhAQwARIhBXPJy6…"}

The real message.content column. No words, ever.

End-to-end means end-to-end

The server relays and stores your message but never holds a key to open it. A database dump, a curious admin, or a subpoena reveals only ciphertext.

STEP 1 · IDENTITY

Every device makes its own keys

The first time you log in, your browser generates a set of Curve25519 keys using KeyHelper. The public halves are uploaded so others can reach you; the private halves are written to IndexedDB and never leave the device.

STEP 2 · THE HANDSHAKE (X3DH)

Agreeing on a secret without meeting

To message Bob — even if he's offline — Alice fetches his public bundle (GET /api/keys/bundle/{bob}) and runs X3DH (Extended Triple Diffie-Hellman). It mixes several key-agreement steps into one shared secret that only Alice and Bob can derive. In the code this is a single call:

new SessionBuilder(store, bob).processPreKey(bundle)

The server hands out one one-time prekey per request and deletes it immediately (an atomic, lock-protected operation), so no two conversations ever reuse the same starter key. When Bob comes online, he reconstructs the identical secret from the header of Alice's first message. Neither had to be online at the same time.

STEP 3 · PER-MESSAGE KEYS (DOUBLE RATCHET)

A fresh key for every single message

Once a session exists, the Double Ratchet derives a brand-new key for each message and destroys it right after use. This is what gives forward secrecy: even if today's key is stolen, yesterday's messages stay locked — their keys no longer exist.

msg 1 · key₁→ burned → msg 2 · key₂→ burned → msg 3 · key₃→ burned → …

Each key encrypts exactly one message. The chain also re-keys with fresh randomness whenever the conversation changes direction, so a compromise can even "heal" over time.

All of this lives inside one call per message — SessionCipher.encrypt() to send, decrypt…() to receive.

STEP 4 · ON THE WIRE

What actually travels & gets stored

The ciphertext is packaged into a small self-describing JSON envelope, base64-encoded, and stored as the message's content. That's the "noise" you saw at the top:

"v": 1, // envelope format version "type": 3, // 3 = first message (carries the X3DH setup) // 1 = every message after (ratchet only) "body": "MyjpAgiRhAQwARIhB…" // base64 ciphertext + auth tag
type 3A PreKeyWhisperMessage — the opening message that bootstraps the session on the recipient's side.
type 1A WhisperMessage — an ordinary ratcheted message once the session is running.

The recipient's browser reverses it: decode base64 → decrypt with the right ratchet key → get back the original text. If decryption fails (tampering, wrong key), it shows [unable to decrypt] rather than guessing.

STEP 5 · READING HISTORY

Why old messages still open after a reload

Here's a subtlety worth calling out. The ratchet destroys each key after one use — so if the app re-decrypted stored ciphertext every time you reopened a chat, it would fail the second time. Aura solves this with a rule:

  1. Decrypt each message exactly once

    The first time a message is seen on this device, it's decrypted with the live ratchet.

  2. Cache the plaintext locally

    The result is stored in the browser's plaintextCache (IndexedDB), keyed by message id.

  3. Serve from cache on reload

    Reopening the chat reads the cache — the ratchet is never re-run, so history is stable and error-free.

A natural consequence, and the correct one: history lives on the device that decrypted it. Real Signal behaves the same way — keys alone can't resurrect old messages.

STEP 6 · CHANGING DEVICES

Your keys, recoverable by password only

Because private keys live in the browser, clearing storage or switching devices would normally lose your identity forever. Aura offers an encrypted backup: your identity keys are encrypted in your browser with a key stretched from your password (PBKDF2, 200,000 rounds) and sealed with AES-GCM, then the opaque blob is uploaded.

Derive key from passwordPBKDF2-SHA-256 · 200k
Encrypt the identity blobAES-256-GCM
Server storesciphertext + salt + iv only
Restore on new devicere-enter password → decrypt

A wrong password simply fails the AES-GCM integrity check — no guessing oracle, no partial data. The server never sees the password or the keys.

HONEST ABOUT THE EDGES

What this does — and doesn't — protect

This is a learning implementation of a real protocol. It genuinely encrypts, but it's not hardened to Signal-the-product's level. Worth knowing:

✓ Direct messages are E2E
1:1 chats use full X3DH + Double Ratchet with forward secrecy.
✕ Group chats are disabled
Group E2E needs a different scheme (sender keys), so groups are turned off rather than sent in the clear.
⚠ Trust on first use
Keys aren't verified via safety numbers yet, so a malicious server could attempt a key swap.
⚠ Backup ≠ forward secrecy
A stolen backup blob plus the password recovers the identity key — use a strong password.
⚠ Needs HTTPS in production
Web Crypto requires a secure context; localhost is fine for dev, real deploys need TLS / wss://.
✓ Server stays blind
It relays and stores ciphertext + public keys only — never plaintext or private keys.

Built with @privacyresearch/libsignal-protocol-typescript (Signal Protocol in the browser via WebCrypto) and the browser's native crypto.subtle for backups. Keys persist in IndexedDB; the Spring Boot backend acts purely as a key directory and blind relay. ◆ Aura security notes.
